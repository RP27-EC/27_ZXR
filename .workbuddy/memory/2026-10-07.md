# 2026-10-07 工作日志

## 下板"能看到遥控值但车不动"的排查结论
- 现象：下板能读遥控（rc_sensor 在线），但四个麦轮不动。
- 根因：非代码问题，是**供电/上电时序**。当时 M3508+C620 电调功率域未真正上电，电机不回传 CAN1 反馈帧（0x201~0x204）。
- 机制：`Chassis_Step()` 里 `Chassis_Is_Wheel_Online()` 要求四轮都 `DEV_ONLINE`；`rm_motor_heart_beat` 计数累加、收帧归零（offline_cnt_max=100，monitor_task 1kHz 调 group_heartbeat → 超时~100ms）。反馈不来→判离线→进 SLEEP 清零扭矩。这是设计正确的失效保护。
- 解决：整车断电再上电，电调带电后开始回传反馈，offline_cnt 归零，状态翻回 ONLINE，联锁解除，车恢复。
- 结论：e42a87e→2043b9f 的改动（车身参数、ROTATE_R 括号、osDelay(5)→(1)、加 Board_Tx 板间通信、CAN2 的 Yaw 反馈 0x001→0x12）均与本次"车不动"无关。osDelay(1) 改动安全，可保留。
- 下次排查顺序：先看 LF_Motor.state->status/offline_cnt 是否 OFFLINE（=电机没回传 CAN，供电/CAN 问题），确认电调功率线带电、CAN 终端电阻在位，再整车断电上电，而非只点 MCU 复位。

## 修正：实际根因是「右后轮 RB 离线」触发全局锁定
- 用户后续确认：并非四轮全离线，而是**只有右后轮 RB（Motor ID=4，CAN1 反馈帧 0x204）离线**，其余三轮 DEV_ONLINE、遥控键值正常。
- 机制：`Chassis_Is_Wheel_Online()` 要求四轮全在线，任一离线即返回 0；`Chassis_Step` 据此进 SLEEP 把四轮扭矩全清零 → 整车不动（即使只有 1 个轮掉线）。这是设计正确的失效保护。
- RB 离线原因（按概率）：① CAN 菊花链最后一节（LB→RB 或 RB 进线）插头松动/接触不良（最可能因"重新上电能好一阵子"印证，间歇性 reconnect）；② RB 电机 DIP 拨码 ID ≠ 4（代码假设 RB=ID4 发 0x204）；③ RB 电调未上电/电机线松。
- 验证：调试器看 RB_Motor.state->status / offline_cnt，若 offline_cnt 涨到 100 卡 OFFLINE 而其余在线，即实锤。
- 处理：硬件修复 RB 的 CAN 插头与 DIP ID(=4)，勿改"任一离线全锁"的安全逻辑（麦轮缺轮运动学崩，锁死才安全）。可加"哪个轮离线"的调试输出以便排查。

## 用户补充："一开控就离线"
- 含义：RB 在临界状态——静止/零电流时勉强在线，一旦被命令出力（s1→中位进入 NORMAL 下发扭矩）或系统一启动就掉线。
- 指向：RB 物理层临界。最可能是 RB 电调功率线接触不良 → 负载电流一来电压跌落(brownout)电调复位 → 反馈消失判离线；其次 RB CAN 链尾插头松 / DIP ID≠4 / 终端电阻未使能。
- 排除：osDelay(1) 非元凶（SLEEP 与 NORMAL 发送节奏相同，且 RB 从开机即离线，早于推摇杆）。
- 排查优先级：① RB 电调功率线/香蕉头 ② RB CAN 进/出插头 ③ RB DIP ID=4 ④ RB 端 120Ω 终端电阻。

## 用户再更正：其实是「四个轮子全离线」，RC 在线
- 用户最终确认：之前说 RB 离线不准确，实际是 LF/LB/RF/RB **四个全 DEV_OFFLINE**，但 rc_sensor 在线。
- 架构说明：RC 走 DBUS/UART（MCU 3.3V 域）与电机 CAN1（FDCAN1，需电调 12V/24V 才回传 0x201~0x204）是独立两路；所以"RC online + 四轮 offline"状态本身合理，固件锁 SLEEP 也正确。但整车正常上电时四轮全离线不正常。
- 四轮全掉（非单轮）→ 指向公共故障：① 可能仅在桌面只给 MCU 上电、未接电机 24V（此时四轮离线属正常，接电机电即可）；② 整车带电仍全掉 = 电机公共链路问题：电机总电源插头松/接触不良、MCU 端 CAN1 线缆松、CAN1 终端电阻缺失、电调未上电。
- 排除代码：CAN1 的 0x201~0x204 收帧逻辑未在改动中触碰，且重上电能好证明 RX 路径 OK；忽好忽坏=接触不良/供电间歇性。
- 验证：整车带电时看四个 motor.state->status 全 OFFLINE 且 offline_cnt 顶 100、rc_sensor 在线，即实锤电机 CAN1/供电公共链路。

## 关键进展：清零 offline_cnt 也救不了 RB → 帧已彻底不来（硬断开）
- 用户实验：早先"把 offline_cnt 清零 + 同时开摇杆"RB 能恢复在线、车能动；现同法**无效**。
- 代码依据（排除软件）：
  - `rm_motor_heart_beat()`(RM_motor.c:140)：offline_cnt 累加，>100 判 DEV_OFFLINE；否则若 status==DEV_OFFLINE 则翻回 DEV_ONLINE。**恢复逻辑正确**，只要帧来就能自动回在线。
  - `rm_motor_update()` 收帧时 `offline_cnt=0`。`CAN1_rxDataHandler` case 0x204→RB_Motor.rx 链路完整。
  - `drv_can.c:164` CAN1 过滤器 MASK 模式、ID1=ID2=0 → 掩码 0，**所有标准帧都收**，0x204 不会被滤。
- 结论：**清零也救不了 = RB 的 0x204 帧已彻底不抵达 MCU**。以前能救=间歇性到帧；现在救不了=硬断开。从"临界接触不良"恶化到"彻底断开"。
- 与"一开控/切云台模式就掉"吻合：RB 疑为 CAN 菊花链末端且终端电阻在其端；1kHz 灌帧时高速反射+接触临界→末端掉线；搬动/振动把插头彻底震脱。若 RB 是链尾带终端，拔掉它还会导致整条 CAN1 失匹、连累 LF/LB/RF（解释之前"四轮全掉"）。
- 排查重点（下车）：① RB CAN 进/出插头按紧插到底 ② RB 端 120Ω 终端电阻（链尾终端缺失会拖垮整条总线）③ RB DIP ID=4 ④ RB 电调功率线/香蕉头虚焊松动。
- 实锤：调试器看 RB_Motor.state->offline_cnt 一路涨到 100 卡死不回 0（而其余三轮在线）→ RB 物理层彻底断。
- 可加调试打印（仅观测，不动驱动/联锁）：直接输出"在线轮子数 N/4 + 具体哪个离线"，省去逐个看变量。

## 新假设：轮子顺序（DIP ID ↔ 物理位置）可能搞反了
- 用户质疑：调试器报"RB 离线"(0x204/DIP4)，但修车的人在实际修**左后轮(LB)**。二者矛盾 → 很可能 DIP ID 与物理安装位置不对应。
- 代码硬假设（Chassis.c + can_protocol.c）：DIP1=LF(0x201)、DIP2=LB(0x202)、DIP3=RF(0x203)、DIP4=RB(0x204)。轮子靠 DIP ID 识别，不靠"角"命名。
- 若修的是物理 LB 而代码报 0x204(DIP4)离线 → DIP4 实际装在左后 → 顺序错位。
- 双重危害：顺序错位不仅改"名"，还会让 `Chassis_Inverse_Kinematics()` 把错误的 wheel_speed 公式喂给错误的物理轮 → 运动学极性全乱 → **极可能就是用户最早报的"麦轮方向错"的同一根因**。
- 实锤方法：上电看哪个 code-name OFFLINE(得 DIP ID) → 看物理坏轮在哪个角 → 对照 DIP；并逐个核对四轮 DIP 拨码。
- 修复：A) 重拨 DIP 为 LF=1/LB=2/RF=3/RB=4（代码不动，但需验每轮转向极性）；B) 改 Chassis.c 的 rxId 对齐真实 DIP。两种都需重新验证四轮转向极性。
- 当前未改文件，等用户上车确认 DIP 实际位置后再动手。
