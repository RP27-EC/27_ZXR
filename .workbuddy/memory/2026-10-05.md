## DM4310 云台串级 PID（自有控制器 + 纯力矩输出）

用户提供《DM-J4310-2EC V1.1 使用说明书 V1.2》，并实现「自己的串级 PID 只输出力矩 + 遥控器控制」。

### 手册关键信息（纠正了之前的错误假设）
- DM-J4310-2EC 是 **10:1 减速电机**；位置/速度/扭矩反馈均为**输出轴侧**（rad / rad·s⁻¹ / N·m）。
  - 空载最大 200 rpm = 20.94 rad/s（输出轴）；转子侧限制 2000 rpm。
- 额定扭矩 **3 N·m**，峰值 **7 N·m**；额定转速 120 rpm。
- **反馈帧 ID = MST_ID，由调试助手设置，默认 0** —— 不是「0x10 + 电机ID」！
  之前从真车反推出的 0x11/0x12 只是真车团队的 MST_ID 配置，并非协议规则。
- 控制帧 ID = ESC_ID（电机 ID）。
- **反馈是问询式**：不发控制帧就不回反馈；且超时会触发「通讯丢失防护」自动退出使能。
- MIT 模式 **Kp=0 且 Kd=0 时，扭矩仅由 t_ff 决定** = 纯扭矩输出。
- 手册警告：用内部位置控制时 **Kd 不能为 0**，否则振荡失控。

### 本工程改动
- 新建 `Application/ConfigLayer/config_gimbal.h`：CAN ID、限幅、串级 PID 参数、遥控映射集中管理。
- `motor.c/h`：用户已加 Pitch_Motor(0x001/CAN1)、Yaw 改 0x002/CAN2；我补了 `order_correction = 1`。
- `can_protocol.c`：修复用户遗留 BUG——原代码把 CAN1 的 0x11 仍路由给 Yaw，
  而 Yaw 已挪到 CAN2 → Yaw 永远收不到反馈。改为 CAN1 `0x11`→Pitch、CAN2 `0x12`→Yaw。
- `control_task.c`：实现 角度环(rad)→速度环(rad/s)→力矩(N·m) 串级，经 `single_set_torque()` 下发。
  遥控：Yaw 用 ch0、Pitch 用 ch1，按 `RC_RATE × dt` 积分成目标角度。
- `monitor_task.c`：加 Yaw/Pitch 心跳（1ms，超时 100 → DEV_OFFLINE）。

## 加关控保护（照下板 Chassis_Step 的模式）

### 【重大发现】上板遥控心跳从未被调用

**已在 monitor_task.c 里补上 `rc_sensor.heart_beat(&rc_sensor);`（1ms）。**
以后新增任何依赖 rc_sensor.work_state 的逻辑，都必须确认这句在跑。

### 关控保护实现（gimbal.c）
- 新增 `gimbal_mode_t { GIMB_MODE_SLEEP, GIMB_MODE_NORMAL }` 和全局 `g_gimbal_mode`
  （初值 SLEEP，上电安全）。两者都 extern，方便 Watch 看状态。
- `Gimbal_Ctrl()` 状态机：
  1. `rc_ok = (rc_sensor.work_state == DEV_ONLINE)`、`motor_ok = Gimbal_Is_Motor_Online()`
     任一不满足 → SLEEP + `Gimbal_Safe()` + return。
  2. 处于 SLEEP 时 → 要求 `RC_IsChannelReset()`（ch0~ch3 死区 50 全回中）才转 NORMAL，
     防止重开控瞬间云台甩到杆位对应角度。开关：`GIMB_RC_RESUME_NEED_CENTER`。
- `Gimbal_Safe()`：清两环积分 + `target_angle = motor_angle_sum` + `inited = 0` + 力矩 0，
  **并且仍然调 `single_set_torque()` 发帧**（问询式反馈，不发会触发通讯丢失防护退出使能）。
- `Gimbal_Axis_Ctrl()` 里原来的 RC_OFFLINE/motor OFFLINE 分支已移除，统一由 Gimbal_Ctrl 管。
- `config_gimbal.h` 新增 `GIMB_RC_RESUME_NEED_CENTER`。

### 左拨杆(s1)使能——用户要求"上拨才控制云台"
- `config_gimbal.h` 新增 `GIMB_ENABLE_S1_POS 1`（1=上）。s1 不在该档位 → SLEEP 卸力。
- `Gimbal_Ctrl()` 判定变成 `!rc_ok || !motor_ok || !sw_on`。

### 【坑】上下板 s1 的类型不同，写法不能互抄

### 为什么云台必须串级而底盘只要单环（用户问过）
底盘的摇杆量**本身就是速度指令**，控制目标是速度 → 一个速度环够。
云台的摇杆量是**角速度**，控制目标是**角度**，必须先积分成目标角度，
再让角度收敛 → 必然多一层角度环。不是实现复杂，是控制对象不同。

## 上板遥控数据来源（用户问"会不会收不到"）

### 当前上板固件链路（完整可用，但依赖硬件接法）
```
DBUS 接收机 → USART3(PC10/PC11) → DMA 双缓冲 + IDLE 中断
→ USART3_rxDataHandler(config_uart.c) → rc_sensor.update() → rc_sensor_info
```
- `rc_sensor_driver.id = DRV_UART3`（rc_sensor.c:31）
- `huart3`: 波特率 **100000**、8 位、**EVEN 校验** = DBUS 标准；引脚 **PC10/PC11**
- `USART3_RX_DATA_FRAME_LEN = 18`（DBUS 一帧 18 字节）✓
- `DRIVER_Init()` 已调 `USART3_Init()`（开 IDLE 中断 + DMAR + DMA 多缓冲）✓

### 【风险结论】会不会收不到？会
- **若接收机插在上板** → 上面的链路直接可用。
- **若接收机插在下板（真车就是这样）→ 上板永远收不到**：
  真车上板是下板解析 DBUS 后经 **CAN 板间帧** (ID_Board_Rx1..4) 转发的，
  真车 `rc_sensor.h` 里 `RC_OFFLINE` 直接定义成
  `(Board_Rx_Info.state_pkt.car_state == 0 || Board_HeartBeat.status == DEV_OFFLINE)`，
  即真车上板**根本没有本地接收机**。
- 而当前 27_ZXR_up 的 `can_protocol.c` **只处理 0x0b / 0x11 / 0x205 / 0x12**，
  **没有任何板间通信 case**，也没有 communicate.c → 没有兜底路径。
- 后果：rc_sensor 恒 DEV_OFFLINE → 关控保护永久触发 → 云台不动。

### 排查方法
Watch 窗口看三个量：
- `rc_sensor_info.ch0` 推摇杆是否变化（不变 = 没收到数据帧）
- `rc_sensor_info.offline_cnt`（一直等于 60 = 从未收到）
- `rc_sensor.work_state`（应为 DEV_ONLINE = 0）
若确认接收机在下板，需照真车补板间通信（下板发 + 上板收 + 心跳）。

## BUG 修复：关控积分清零函数不存在（链接报错）
用户指出 `Gimbal_Safe()` 里调用的 `integral_to_zero()` 在上板工程里**只有 PID.h 声明、没有 PID.c 定义**
→ 链接阶段 undefined reference，构建必挂。且该函数名与下板 `pid_clear()` 不一致。
- 已删除 PID.h 第 24 行的 `integral_to_zero` 悬空声明，改为 `pid_clear(pid_ctrl_t*)`。
- PID.c 新增 `pid_clear()` 定义：`pid->integral = 0.f;`（与下板 chassis 的 `pid_clear` 逐字一致）。
- gimbal.c `Gimbal_Safe()` 两处 `integral_to_zero(...)` 改为 `pid_clear(&axis->ag_pid/sp_pid)`。
- 说明：只清 `integral`（抗积分饱和）即足够；pout/iout/dout/out 由 `single_pid_ctrl` 每帧重算，
  `last_err` 在重进 NORMAL 时因 `Gimbal_Target_Update` 把 target 对齐 measure（err≈0）不会造成微分尖峰。
